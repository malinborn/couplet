# Атомарная запись, права файла и TCC — расследование

**Дата:** 2026-09-12 · **Issues:** #21 (повторные запросы TCC), #18 (сброс прав) · **Статус:** расследование завершено, код не менялся

> **Продакшн-код не тронут.** `write_file` остался как есть. Ниже — измерения и рекомендация; решение за владельцем.

---

## TL;DR

| Утверждение из #21 | Вердикт |
|---|---|
| `write_file` подменяет файл новым inode на каждом сохранении | **Подтверждено** — измерено, каждое сохранение даёт новый inode |
| Права оригинала не копируются, файл получает `0644 & ~umask` | **Подтверждено** — `0600 → 0644`, `0640 → 0644` |
| Extended attributes теряются | **Подтверждено частично** — обычные xattr теряются; `com.apple.metadata:*` (теги Finder, where-froms) восстанавливает Spotlight |
| ACL теряются | **Подтверждено** — и хуже: ACL `deny delete` ломает сохранение целиком |
| Это тот же корень, что #18 | **Подтверждено** |
| Смена inode ломает TCC-разрешение и вызывает повторные запросы | **НЕ подтверждено. Скорее всего неверно.** |

**Главный вывод:** #18 — реальный баг ровно с той причиной, что описана в issue. #21 — **другой баг с другой причиной**: приложение подписано ad-hoc (linker-signed), без Team ID и без designated requirement, и TCC видит **новый клиент при каждом релизе**. Смена inode здесь ни при чём.

Из этого следует, что **вариант C теряет своё главное обоснование**: он предлагался, чтобы починить TCC, а TCC он не чинит.

## Метод

Гонял на `md-mini-dev` (`npm run dev:app`, identifier `com.md-mini.dev`, свой data-dir и свой сокет) — установленное продакшн-приложение владельца не затрагивалось. Продакшн-сборка (`npm run tauri build`) и `npm run tauri dev` не запускались; `mcp-bridge` не включался.

Каталог: `~/Documents/mdmini-g4-repro/` (TCC-защищённая локация). `umask` = `022`.

Сохранения провоцировались через реальный путь приложения — не прямым вызовом Rust-функции:

```
printf '...' | md-mini ai edit <file> --socket /tmp/md_mini_dev_cmd.sock
```

`ai edit` кладёт содержимое в буфер → `handleChange` → `fileState.isDirty = true` → autosave (300 мс) → `invoke('write_file')`. То есть измеряется именно тот код, о котором issue.

Приложение перезапускалось между сериями сохранений (см. «Сценарий 7»).

### Сценарий 3 — тег Finder (`com.apple.metadata:_kMDItemUserTags`)

`tagged.md`: inode `27591585 → 27591655`, mode `0644`, тег `Red` **пережил** замену — `mdls` после сохранения по-прежнему показывает `kMDItemUserTags = (Red)`.

**Вывод по xattr:** теряется всё, кроме `com.apple.metadata:*` — их `mdworker` переписывает обратно из индекса Spotlight по пути. То есть «теги Finder не ломаются» — это случайность, а не свойство кода; на томе с выключенным Spotlight они тоже пропадут.

### Сценарий 4 — ACL

**4a, разрешающий ACL** (`staff allow read`), `acl2.md`:

| Свойство | До | После |
|---|---|---|
| inode | `27591752` | `27591788` |
| ACL | `0: group:staff allow read` | **отсутствует** (флаг `+` в `ls -le` пропал) |

**4b, запрещающий ACL** (`everyone deny delete`), `handmade.md` — **новая находка, в issue её нет:**

```
mv: rename /tmp/g4tmp.md to …/handmade.md: Permission denied
```

`rename` над файлом с `deny delete` возвращает EPERM, потому что замена требует права удалить цель. Значит md-mini **вообще не может сохранить такой файл**. Файл остался нетронутым (inode `27586960`, mode `0600`, ACL на месте, `.tmp` подчищен).

Хуже всего то, как это выглядит для пользователя. `App.svelte:180`:

```ts
} catch (err) {
  console.error('Auto-save failed:', err);
}
```

Ошибка уходит только в консоль. Тоста нет, индикатор «сохранено» не меняет смысла, пользователь продолжает печатать в уверенности, что всё на диске. Запись в подобный файл через `OpenOptions::write` прошла бы нормально — то есть сейчас атомарная схема не просто теряет метаданные, она делает часть файлов недоступными для записи.

### Сценарий 5 — символическая ссылка (в issue не упомянуто)

`link.md → target-real.md`, редактируем `link.md`:

| Свойство | До | После |
|---|---|---|
| `link.md` | симлинк (`lrwxr-xr-x`) | **обычный файл** `-rw-r--r--`, 46 байт |
| `target-real.md` | inode `27588107`, содержит правку? | inode `27588107`, **не изменился** |

`rename` заменяет саму ссылку, а не её цель. Правка пользователя уходит «не туда», симлинк уничтожается. Для сетапов с симлинками (дотфайлы, Obsidian-вольты, ссылки в синкающиеся папки) это тихая потеря данных.

### Сценарий 6 — жёсткая ссылка (в issue не упомянуто)

`hard.md` и `target-real.md` — одна инода, `links=2`. После правки `hard.md`:

| Файл | До | После |
|---|---|---|
| `target-real.md` | inode `27588107`, links=2 | inode `27588107`, **links=1**, содержимое старое |
| `hard.md` | inode `27588107` | inode `27589246`, links=1, новое содержимое |

Связь разорвана, файлы разъехались.

### Сценарий 7 — файл, созданный самим md-mini, серия сохранений, перезапуск приложения

`born.md` создан через md-mini (сразу `0644`). Ставим `0600`, сохраняем дважды:

| Шаг | inode | mode |
|---|---|---|
| создание | `27589296` | 0644 |
| после `chmod 600` + сохранение A | `27589361` | **0644** |
| сохранение B | `27589381` | 0644 |

Inode меняется **на каждом** сохранении, не только на первом. Для файла, который md-mini создал сам, симптом #18 виден так же — достаточно один раз поставить свои права.

После полного перезапуска приложения (`pkill`, чистый старт, новый сокет) поведение идентично: `handmade3.md` `27587283 → 27591399`, `0600 → 0644`.

## Часть про TCC: гипотеза не подтвердилась

### Что измерено

За две сессии приложения и 8 сохранений в `~/Documents` в `tccd` **не было ни одного запроса** к `kTCCServiceSystemPolicyDocumentsFolder`:

```
$ /usr/bin/log show --last 6m --predicate 'process == "tccd"' --info | grep -c DocumentsFolder
0
```

Единственные TCC-запросы от процесса md-mini — `kTCCServiceListenEvent` и `kTCCServiceMicrophone` (обычное прощупывание со стороны WebKit). Подмена inode не вызвала переоценки прав ни разу.

**Честная оговорка.** Под `tauri dev` бинарник запущен из терминала, и TCC назначает ответственным процессом iTerm:

```
AUTHREQ_ATTRIBUTION: attribution={
  responsible={identifier=com.googlecode.iterm2, …},
  requesting={identifier=md_mini-0e6362a92e6f6e04,
              binary_path=…/shared-target/debug/md-mini}}
```

То есть решения принимались по грантам iTerm. Отсутствие запроса — сильное свидетельство, но не доказательство: под запуском из Finder/LaunchServices атрибуция была бы на само приложение. Полный репро именно всплывающего диалога требует подписанного бандла, запуска через LaunchServices и живого человека, который нажмёт кнопку в модалке, — ночью без владельца это невыполнимо.

Архитектурно у гипотезы «inode ломает TCC» тоже нет опоры: `kTCCServiceSystemPolicyDocumentsFolder` — это грант **на папку для клиента-приложения**, в TCC нет ни файловых путей, ни инод. Приложение не сэндбоксится (`codesign -d --entitlements -` возвращает пусто), поэтому powerbox-грантов на отдельные файлы и security-scoped bookmarks здесь тоже не существует.

### Что, по всей видимости, является настоящей причиной

md-mini не подписан:

```
$ codesign -dvvv /Applications/md-mini.app
Identifier=md_mini-db6645b7628eb60a
CodeDirectory v=20400 flags=0x20002(adhoc,linker-signed)
Signature=adhoc
TeamIdentifier=not set
Internal requirements=none
Info.plist=not bound
Sealed Resources=none

$ codesign -d -r- /Applications/md-mini.app
/Applications/md-mini.app: code object is not signed at all
```

Designated requirement у приложения **нет вообще**. Для такого клиента TCC нечем идентифицировать приложение, кроме cdhash и linker-signed identifier — а они меняются от сборки к сборке.

Сравнение выпущенных версий (DMG из кэша Homebrew):

| Версия | `Identifier` | `CDHash` |
|---|---|---|
| 0.2.0 (aarch64) | `md_mini-e5d59451e3576f17` | `d1d7d7447e5d526df756302475733c795aca1813` |
| 0.3.5 (aarch64) | `md_mini-e5d59451e3576f17` | `3fe047dd1a2bbb54f6497e539b1b5d6d2af7c58d` |
| 1.1.0 (universal) | `md_mini-db6645b7628eb60a` | `7fbdf8199309d933880c6fcac8cda4cd7c5e2af5` |
| 1.1.0 установленное | `md_mini-db6645b7628eb60a` | `7fbdf8199309d933880c6fcac8cda4cd7c5e2af5` |
| dev-сборка | `md_mini-0e6362a92e6f6e04` | (debug) |

Читается так: **cdhash меняется на каждом релизе**, identifier — как минимум при смене архитектуры сборки. Установленная 1.1.0 побайтово совпадает с DMG той же версии — значит идентичность стабильна *внутри* версии и ломается *между* версиями.

Это ровно тот профиль симптома, который описан в #21: «раз по 5 одно и то же». Каждое обновление md-mini (а релизы через `brew-release` частые) macOS видит как **новое, незнакомое приложение** и запрашивает доступ к папке заново. С заменой inode это не связано никак.

**Проверочный вопрос владельцу:** повторные запросы совпадали по времени с обновлениями md-mini (`brew upgrade`), а не с обычным редактированием после паузы? Если да — диагноз подтверждён окончательно.

## Побочные находки

- **`.tmp` создаётся с правами `0644`.** `fs::write` создаёт временный файл по umask. Для документа с правами `0600` (чужой секрет, приватная заметка) содержимое оказывается доступным на чтение всем — и не «на мгновение», а навсегда, потому что именно этот файл и становится документом. Для проекта, где владелец — Head of Infrastructure & Security, это стоит считать отдельным дефектом.
- **`.tmp` лежит рядом с документом** (`format!("{}.tmp", path)`), виден в Finder и попадает в очередь iCloud/Dropbox — как и сказано в issue.
- **Ни `fsync` файла, ни `fsync` каталога нет.** Текущая схема защищает от краха процесса, но не от потери питания: `rename` может не дойти до диска.
- **Та же форма записи в `comments.rs`** (`write_atomic`, sidecar рядом с документом). Ставки ниже — файл целиком принадлежит md-mini, — но при фиксe стоит пройтись и там. `recovery.rs` и `session.rs` пишут в app-data-каталог, там tmp+rename уместен и менять его не нужно.

  > **Поправка от 2026-09-12, внесена при реализации #54.** «Ставки ниже» больше не верно. После #23 и #36 sidecar хранит черновик реплики, который человек набирает и ещё не отправил, — а у него, в отличие от документа, нет ни `isDirty`, перезапускающего запись, ни снапшота в `recovery.rs`. То есть у sidecar'а ставки как раз **выше**: единственная копия текста лежит в этом файле. Починено в #54 — общий модуль `src-tauri/src/atomic_write.rs`, два вызывающих (`commands.rs` и `comments.rs`), второй реализации нет.
  >
  > Попутно нашлось то, чего в этом расследовании не было: старое временное имя (`path.with_extension("tmp")`) давало `.mdmini_comments_spec.tmp`, которое проходит проверку `is_sidecar` — значит `collect_open` мог распарсить недописанный временный файл как настоящие треды, а `mdmini watch` — сработать на него. Комментарий в `watch.rs` утверждал обратное. Теперь имя начинается с двух точек и не совпадает ни с чем.

## Рекомендация

### Вариант A с дополнениями — и отдельный issue на подпись

Предлагаю **A**, а не C, ровно потому, что измерения убрали обоснование C.

**Что делать по A:**

1. Создавать tmp через `OpenOptions::new().write(true).create_new(true).mode(0o600)` — не `fs::write`, чтобы не было окна с правами 0644.
2. Перед `rename` перенести метаданные с оригинала на tmp: `libc::copyfile(orig, tmp, NULL, COPYFILE_ACL | COPYFILE_XATTR)`, а режим и владельца восстановить явно через `fchmod`/`fchown`.

   > **Поправка от 2026-09-12, внесена при реализации #18.** В первой редакции здесь стояло `COPYFILE_SECURITY | COPYFILE_XATTR` с оговоркой «`COPYFILE_STAT` не брать». Эта комбинация невыразима: в `copyfile.h` определено `COPYFILE_SECURITY (COPYFILE_STAT | COPYFILE_ACL)`, то есть `SECURITY` **уже содержит** `STAT`, а `SECURITY|XATTR` — это буквально `COPYFILE_METADATA`. Следование исходной формулировке скопировало бы старый mtime, то есть ровно ту поломку watcher'а, от которой абзац и предостерегал.
   >
   > **`COPYFILE_STAT` не брать** остаётся верным по сути: свежесохранённый файл должен иметь новый mtime, иначе поедут file watcher и логика «файл изменился снаружи». Достигается это через `COPYFILE_ACL | COPYFILE_XATTR` плюс явные `fchmod`/`fchown`, а не через `SECURITY`. Проверяется тестом `updates_mtime_rather_than_copying_the_old_one`.
3. Резолвить симлинки до записи (`fs::canonicalize`, с явной обработкой случая «цели ещё нет») — чинит сценарий 5.
4. Прятать tmp: `.<имя>.tmp` или случайный суффикс в том же каталоге — чтобы не светился в Finder и синхронизациях.
5. `sync_all()` на файле перед `rename` и `fsync` каталога после — закрывает потерю питания.
6. **Показывать ошибку сохранения пользователю** (тост), а не только `console.error`. Это чинит сценарий 4b: файл с `deny delete` всё ещё не сохранится, но пользователь об этом узнает, а не потеряет работу молча.

Что A **не** чинит: смену inode, разрыв жёстких ссылок, невозможность записи при `deny delete` ACL. И не чинит TCC — но TCC не чинит ни один из трёх вариантов.

### Почему не B

Чистая запись на месте (`truncate` + `write`) даёт inode, права, xattr и ACL бесплатно и чинит сценарии 4b, 5, 6. Цена — атомарность, и цена эта выше, чем кажется на первый взгляд:

- autosave срабатывает каждые 300 мс, то есть окно «файл обрезан» открывается десятки раз в минуту;
- `delete_recovery` вызывается **после каждого удачного сохранения**, поэтому между сохранениями recovery-снапшота не существует вовсе. Утверждение «цена B уже оплачена recovery-слоем» в текущем виде неверно: recovery снимается раз в 5 секунд и стирается при каждом сохранении. Крах ровно в момент записи застаёт систему в состоянии «файл обрезан, снапшота нет».

B становится допустимым только вместе с переделкой протокола recovery (снапшот **перед** разрушающей записью, удаление — только после успешного `fsync`). Это и есть C.

### Почему не C сейчас

C — правильная конструкция, если inode обязан сохраняться. Измерения говорят, что ради TCC он сохраняться не обязан. Остаётся выигрыш по жёстким ссылкам и по открытым дескрипторам чужих процессов (`tail -f`, синхронизаторы) — реальный, но узкий, и он не стоит двух веток логики в единственном месте кода, где живёт несохранённая работа человека. Если C всё же выбирают, обязательное условие — переработка recovery по пункту выше.

### Отдельно: #21 закрывается подписью, а не записью

Настоящий фикс повторных запросов TCC — стабильная идентичность приложения: Developer ID Application signing + hardened runtime + нотаризация, с `signingIdentity` в `tauri.conf.json`. Тогда TCC записывает грант на requirement с Team ID, и он переживает обновления. Это отдельная задача (нужен платный Apple Developer Program), и её стоит вынести в свой issue, не смешивая с #18.

## План тестов для будущего фикса

Существующие тесты трогать не пришлось: `cargo test` — 156 passed, `npx vitest run --dir src` — 605 passed.

**Unit (Rust, `commands.rs`):**

1. `0600` остаётся `0600` после сохранения; `0640` остаётся `0640`.
2. ACL переживает сохранение (`acl_get_file` до и после, либо проверка флага `+`).
3. Пользовательский xattr (`com.mdmini.test`) переживает сохранение.
4. `com.apple.quarantine` переживает сохранение.
5. mtime **обновляется**, а не копируется со старого файла (регрессия на `COPYFILE_STAT`).
6. Временный файл ни в один момент не шире прав оригинала: при umask `022` и оригинале `0600` промежуточный файл не должен быть `0644`. Проверяется через seam — функцию записи с хуком, вызываемым после создания tmp и до `rename`.
7. Запись через симлинк сохраняет симлинк и обновляет цель.
8. Запись в файл с ACL `everyone deny delete` либо проходит, либо возвращает `Err` — и никогда не рапортует успех.
9. Для варианта B/C: inode не меняется, число жёстких ссылок сохраняется.

**Крах в момент записи — обязательный тест, без него фикс принимать нельзя:**

10. *Инъекция сбоя.* Вынести seam (`write_file_with_hooks`), уронить запись между `write` и `rename`. Инвариант: оригинал **побайтово** не изменился, временный файл подчищен.
11. *Настоящий SIGKILL.* Интеграционный тест: дочерний процесс пишет большой документ, родитель убивает его `SIGKILL` в середине. После этого файл должен быть либо полностью старым, либо полностью новым — состояние «обрезан» недопустимо. Для in-place вариантов допускается «обрезан **при наличии** полного recovery-снапшота», и тест обязан проверить наличие и целостность снапшота.
12. *Порядок recovery.* Для B/C: снапшот существует на диске **до** начала разрушающей записи и удаляется **только** после успешного `fsync` + `rename`. Проверяется тем же seam-хуком.
13. *Потеря питания (прокси).* Проверить, что `sync_all()` на файле и `fsync` каталога вызываются до возврата `Ok` — тестируется на уровне seam, без реального обесточивания.

**Фронтенд (vitest):**

14. Ошибка `write_file` порождает тост и оставляет `isDirty = true` (сейчас поднимает только `console.error`).

**Ручная проверка:**

15. Файл в `~/Documents` с `chmod 600`: редактирование в `npm run dev:app`, `stat` до и после.
16. Watcher не реагирует на собственное сохранение (защита `isSaving`, 600 мс) — форма записи меняется, значит и FSEvent-поток меняется.

## Чего проверить не удалось

- **Живой TCC-диалог.** Нужен подписанный бандл, запуск через LaunchServices и человек, нажимающий кнопку в модальном окне. Ночью без владельца — нет.
- **Содержимое `TCC.db`.** `~/Library/Application Support/com.apple.TCC/TCC.db` требует Full Disk Access для терминала; `authorization denied`. Поэтому нельзя показать конкретную строку гранта и её `csreq`.
- **Корреляция запросов с обновлениями.** Нужен ответ владельца: совпадали ли повторные запросы с `brew upgrade`.
- **iCloud Drive и Dropbox.** Поведение `.tmp` и замены inode внутри синкающихся папок не проверялось; там возможны свои эффекты (конфликтные копии, лишние ревизии).
- **Сетевые тома (SMB/NFS).** Семантика `rename` и ACL там другая.
